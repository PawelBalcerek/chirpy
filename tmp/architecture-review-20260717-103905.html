Two adapters justify the seam: Postgres in prod, in-memory in tests.

Problem: Every handler takes *database.Queries — a concrete sqlc-generated type. There is no seam. Handlers are untestable without PostgreSQL.

Solution: Define a Store interface listing the ~12 query methods handlers actually call. *database.Queries already satisfies it. Write an in-memory adapter for tests.

  • two adapters justify the seam: Postgres adapter (prod) + in-memory adapter (tests)
  • leverage: one interface, all handlers testable
  • locality: SQL changes stay behind the adapter; handler tests never break
  • zero handler tests today: this seam makes them possible

  • testable: pure function, no dependencies

After — modules own their routes

CHIRP MODULE → RegisterRoutes(mux)
USER MODULE → RegisterRoutes(mux)
Admin + health (unchanged)

main.go just constructs modules and calls RegisterRoutes. One thick band per domain.

Problem: main.go manually constructs 10 handler structs, repeating DbQueries and JWTSecret fields across them. It's a shallow pass-through — the interface (all those struct fields) is as wide as the implementation (field assignment).

Solution: Each domain module exposes RegisterRoutes(mux, deps). main.go constructs two modules and calls their registration. Routes become internal to the module.

  • leverage: add a route? Change the module, not main.go
  • locality: chirp routes live next to chirp logic
  • interface shrinks: main.go's knowledge drops from 12 handlers to 2 module constructors

Top recommendation

Start with Candidate 3 — Introduce a Store seam. It's the prerequisite for everything else: without a seam between handlers and the database, handlers can't be tested, the domain modules from Candidate 1 can't be verified, and the auth middleware from Candidate 2 has no test surface to protect. Two adapters (Postgres + in-memory) justify the seam. Once the seam exists, candidates 1, 2, and 4 become natural follow-ups.
